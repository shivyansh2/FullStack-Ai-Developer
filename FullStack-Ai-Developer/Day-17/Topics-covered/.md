## 📅 Day 17 — MongoDB, System Design & AI Integration

### 🗄️ Main Topic — MongoDB + Mongoose

**MongoDB architecture**
- **Database:** the top-level container for your data. Example: `taskflow`.
- **Collection:** a group of related documents, similar to a table. Example: `users`, `tasks`.
- **Document:** one record stored as a JSON-like object. Example: a single task with a title, status, and owner.

**SQL vs NoSQL**
- **SQL:** fixed schema, tables, and joins. Best when data is highly relational and consistency rules are strict.
- **NoSQL (MongoDB):** flexible schema and nested documents. Best when data shapes evolve quickly and you read related data together.

**BSON vs JSON**
- **JSON:** the text format you send over HTTP.
- **BSON:** the binary format MongoDB stores internally, with extra types such as `ObjectId` and `Date`.

**Mongoose concepts**
- **Schema:** defines the structure, types, validation, and defaults of a document.
- **Model:** the class built from a schema that you use to query and create documents.
- **Validation and defaults:** `required`, `enum`, `minlength`, and values like `status: "todo"` applied automatically.

**Queries you must know**
`find()`, `findOne()`, `findById()`, `create()`, `findByIdAndUpdate()`, `findByIdAndDelete()`

**Query tuning:** filtering, sorting, pagination (`skip` and `limit`), and projections (`select`).

**Indexes and relationships**
- **Unique index:** stops duplicate emails at the database level. Duplicate key errors (code `11000`) should return `409`.
- **Referencing:** each task stores its owner's `ObjectId`, linking it to a user.

**Connections:** keep the connection string in an environment variable and handle connection failures cleanly.

### 🏗️ System Design — How a Real Backend Handles Requests

**Request flow:** Client → Load balancer → Middleware (logging, CORS, rate limit, auth) → Route → Controller → Service → Model → Connection pool → MongoDB

**Controller vs service vs model**
- **Controller:** handles HTTP input and output.
- **Service:** holds business logic.
- **Model:** talks to the database.

**Key concepts**
- **Connection pooling** — reuse open database connections instead of creating one per request.
- **Stateless authentication** — JWT lets any server instance verify a user without shared session storage.
- **Indexing** — speeds up reads but costs storage and slows writes. *Example: index `owner` and `status` because tasks are filtered by them.*
- **Pagination** — offset-based is simple but slows on large data; cursor-based stays fast and consistent.
- **Scaling** — vertical means a bigger machine; horizontal means more machines behind a load balancer.
- **Caching** — Redis suits frequently read, rarely changed data.
- **Rate limiting and security** — protect the API from abuse and brute-force attempts.
- **Logging and monitoring** — make failures visible and debuggable.

### 🤖 AI Engineering — Connecting AI to a Backend
- **LLM fundamentals** — tokens, context windows, and prompts
- **Server-side calls** — AI requests happen on the backend, never in the browser
- **Secret handling** — keep API keys in environment variables
- **Structured JSON output** — request a fixed format so responses are easy to validate
- **Validation** — check user input before sending it and check model output before using it
- **Cost and latency** — monitor token usage and response time
- **Reliability** — use timeouts, retries, and rate limit handling
- **Hallucination risk** — the model can invent ids, values, or reasons

**Practical task:** Plan a TaskFlow endpoint that accepts a list of tasks and returns suggested priorities with explanations. Start with a mock service before connecting a real LLM API.


> **Rule to remember:** AI output is untrusted input. Fetch tasks from the database by owner, then validate the model's response against a schema before returning it.
